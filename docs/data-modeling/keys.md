# Keys — Natural, Surrogate, Business

> *Additional source: Claudia Imhoff et al., "Mastering Data Warehouse Design" (2003), Ch. 5*

## The key problem: inconsistent definitions across systems

In the real world, an entity like "Customer" is rarely defined consistently across source systems. Common problems:

- **Inconsistent business definition** — the CRM defines a customer as any company that has signed a contract; the ERP defines it as any company that has placed an order. The same company may appear in one system but not the other.
- **Inconsistent system definition** — the same company is stored as separate records for different roles: HQ, branch, ship-to address, billing address.
- **Inconsistent identifier** — System A uses an integer `AccountID`, System B uses a varchar `CustomerCode`, neither is globally unique.
- **External data** — third-party data (credit bureaus, industry codes) use their own identifiers with no overlap.

The data warehouse must resolve these inconsistencies into a single, coherent definition and a single identifier.

---

## Natural key (source key)

The identifier that exists in the source system.

- `CustomerID` from CRM, `OrderNumber` from ERP, `ProductSKU` from the product catalog
- May be a string, GUID, or integer
- Can change if the source system changes (mergers, re-keying)
- May not be unique across sources (two systems using overlapping numeric IDs)

## Business key

A natural key that is stable and meaningful across the enterprise — often the same as the natural key, sometimes a combination.

- `IBAN` for a bank account, `VIN` for a vehicle, `VAT number` for a company
- Used in **Data Vault Hubs** as the anchor for an entity

## Three strategies for choosing a DWH key

When building the DWH system model, choose one strategy per entity:

### 1. Key from the system of record

Use the natural key from the single authoritative source system.

- Works when one system is indisputably "the source of truth" and all others replicate from it
- **Problem:** if the source re-keys (e.g. database migration), the DWH key must change too — breaking fact table FK chains
- **Problem:** if there is no true system of record (multiple co-equal systems), this strategy fails

### 2. Key from a recognized standard

Use an industry-standard identifier that exists outside all systems: IBAN (bank account), VIN (vehicle), ISIN (security), EAN barcode.

- Globally unique and meaningful — survives system changes
- **Problem:** not every entity has an applicable standard (employee, customer, product are often not standardized)
- **Problem:** standards themselves can change or have regional variations

### 3. Surrogate key

A system-generated integer with no business meaning. The DWH generates it, not the source.

- **Small and compact** — a 4-byte integer; faster joins than a 30-character string key
- **Stable** — never changes, regardless of what happens in source systems
- **Eliminates compound keys** — a customer uniquely identified by (Region, BranchCode, AccountID) in the source becomes a single integer SK
- **Consistent** — the DWH, not the source, controls the keying strategy; all fact tables use the same SK domain
- The natural key is retained on the dimension row as an **alternate key** (also called business key) for lookup and back-reference — it is not discarded

Surrogate keys are the recommended strategy for most entities in a data warehouse.

---

## Surrogate key (SK)

A system-generated integer or GUID with no business meaning. Generated by the DWH itself.

- `CustomerKey = 1, 2, 3, ...` (auto-increment) or a hash
- Never changes — stable even if the source system re-keys or merges
- Used as the primary key in dimension tables
- Fact table foreign keys always point to surrogate keys, not natural keys

```sql
-- Dimension: surrogate key is the PK
CREATE TABLE DimCustomer (
    CustomerKey  INT          NOT NULL,  -- surrogate (DWH-generated)
    CustomerBK   VARCHAR(50)  NOT NULL,  -- business key (from source)
    CustomerName VARCHAR(200) NOT NULL
);

-- Fact: references surrogate key
CREATE TABLE FactSales (
    CustomerKey  INT NOT NULL,           -- FK to DimCustomer.CustomerKey
    ...
);
```

## Why surrogate keys matter for SCD2

When a customer's attributes change and a new row is created (SCD2), the new row gets a new surrogate key. The fact table row for a past sale still points to the old surrogate key — so the historical sale correctly reports the old dimension values.

If you used the natural key as the FK, you'd lose that historical accuracy.

## Hash keys (Data Vault)

Data Vault uses **hashed business keys** as surrogate keys — typically SHA-256 or MD5 of the business key string. This allows parallel loading without a central sequence generator.

```sql
HASHBYTES('SHA2_256', UPPER(TRIM(CustomerBK)))
```

## Dimensional conformance

When multiple fact tables share a dimension (e.g. both FactSales and FactInventory join to DimProduct), the same surrogate key value in both fact tables must mean exactly the same product.

**Rule:** `ProductKey = 42` in FactSales and `ProductKey = 42` in FactInventory must refer to the identical product, with identical attribute definitions.

This is called **dimensional conformance**. It is what makes drill-across queries (combining measures from two fact tables) meaningful. If each fact table's DimProduct is independently keyed, a CustomerKey=42 in one table is unrelated to CustomerKey=42 in another — the drill-across produces garbage.

Conformance is achieved by having a **single master dimension** that is shared (same surrogate keys, same attributes) across all fact tables that reference it. In the entity/relational DWH layer, the conformed dimension is defined once; data marts may receive a subset of its attributes but must preserve the original SK values.

## Parallel surrogate key generation

The standard sequential IDENTITY generator fails under parallel ETL — two workers running simultaneously can each read the same `MAX(SK)` and generate colliding keys. Three approaches resolve this:

### Range partitioning — int-safe

Reserve a slice of the integer key space per worker: a fixed-width worker-ID prefix followed by a row counter. With a 3-digit prefix and 7-digit counter the composite stays within `INT` range (max ~10^9 vs INT_MAX ~2.1×10^9).

```
Worker 1 generates keys: 001_0000001, 001_0000002, ...
Worker 2 generates keys: 002_0000001, 002_0000002, ...
```

Keys are collision-free without any coordinator. The SK column stays `int NOT NULL`.

### Range partitioning — bigint

Same prefix scheme but with a 14-digit counter (prefix=3 + counter=14 → up to 10^16, exceeding INT_MAX). The SK column **must be `bigint NOT NULL`** — `int` causes an arithmetic overflow on the first full-load INSERT.

**Caution:** a DEV environment with pre-loaded data runs only UPDATEs and never overflows, so the bug surfaces only on a clean PPE/PROD reload.

**Design preference:** use the int-safe variant for new parallel loads. Migrating from bigint to int after data has been loaded requires dropping and recreating the SK column, which breaks all downstream FK joins.

### Hash keys (Data Vault)

Hash the business key using `SHA2_256` of the concatenated natural key. No central coordinator needed; the hash is deterministic — the same natural key always produces the same surrogate, making loads naturally idempotent.

```sql
HASHBYTES('SHA2_256', UPPER(TRIM(CAST(CustomerBK AS VARCHAR(500)))))
```

Downside: the hash is opaque and large (binary(32)). The natural key must be retained alongside it for human-readable lookups. Standard in Data Vault; less common in Kimball / enterprise DWH stacks.

## Key strategy comparison

| Strategy | Uniqueness scope | Changes with source? | Business meaning? | Best for |
|---|---|---|---|---|
| System of record key | Within that system | Yes | Sometimes | When one system is indisputably authoritative |
| Recognized standard | Global | Rarely | Yes | Entities with universal industry IDs |
| Surrogate key | DWH-wide | Never | No | Most DWH entities |
| Hash key (Data Vault) | DWH-wide | Never | No (derived from BK) | Parallel loads in Data Vault |

---

## Summary

| Key type | Lives in | Changes? | Business meaning? |
|---|---|---|---|
| Natural key | Source system | Sometimes | Yes |
| Business key | DWH / Data Vault Hub | Rarely | Yes |
| Surrogate key | DWH dimension | Never | No |
| Hash key | Data Vault Hub | Never | No (derived from BK) |
